## 1. TLV 一覽

| cmd | 線上 bytes (LE) | size | 角色 |
|------|-----------------|------|------|
| `0x00005029` | `29 50 00 00` | 24 | **治療事件**（每個治療目標一筆） |
| `0x0000502A` | `2a 50 00 00` | 16 | **本地玩家被治療旗標**（非獨立事件） |
| `0x00004EED` | `ed 4e 00 00` | 24 | **護盾增量事件** |
| `0x0001B1B3` | `b3 b1 01 00` | 24 | **護盾當前總量**（狀態同步） |

---

## 2. 0x5029 — 治療事件（權威來源）

### 2.1 結構（payload 24 bytes）

| payload offset | 長度 | 意義 | 樣本 |
|---|---|---|---|
| 0 | 1 | tag | `00` |
| **1..8** | **8** | **★ target_id（治療目標的角色 ID, uint64 LE）** | `9a d9 a0 00 00 00 00 00` = 0xA0D99A |
| 9..16 | 8 | session_token（本 client 的 self-token, 每 session 固定） | `00 00 20 00 00 00 00 00` = 0x200000 |
| **17..20** | **4** | **★ heal 數值（uint32 LE）** | `0f 00 00 00` = 15 |
| 21..23 | 3 | pad | `00 00 00` |

TLV 總長 = 8 + 24 = **32 bytes**。

### 2.2 語意

- **每個 0x5029 = 一次獨立治療事件**。
- 同一 TCP payload 內可以出現**多個 0x5029**，各自對應不同 target（例如「防護」同時治 A 和 B → 兩筆 0x5029）。
- `target_id` 是「誰接收了這次治療」，**不是**施法者。
- `session_token` 在整個 session 中恆定，跨 session 會變。

### 2.3 target_id 樣本對照

| session | 角色 | 觀測到的 target_id |
|---|---|---|
| WS-治癒（單人自癒） | A | `0xA0D99A` |
| WS-治癒隊友 | A（本地）| `0x8D2B3A` |
| WS-治癒隊友 | B（隊友）| `0x8D2BA0` |

Mabinogi entity handle 每次登入重新分配，不能硬編碼。

## 3. 0x502A — 本地玩家被治療旗標

### 3.1 結構（payload 16 bytes）

| payload offset | 長度 | 意義 | 樣本 |
|---|---|---|---|
| 0 | 1 | tag | `00` |
| 1..8 | 8 | session_token（與同 session 的 0x5029.session_token 相同） | `00 00 20 00 00 00 00 00` |
| **9..12** | **4** | heal 數值（uint32 LE，用來對應是哪一筆 0x5029） | `0f 00 00 00` = 15 |
| 13..15 | 3 | pad | – |

TLV 總長 = 8 + 16 = **24 bytes**。

### 3.2 語意（**重要修正**）

**0x502A 不是治療事件本身**，只是「本地玩家在這批事件裡被治療了」的旗標。

判準（實測全對）：
| 情境 | 本地玩家被治療? | 0x502A 出現? |
|------|:-:|:-:|
| 生命連結對敵（治自己） | ✅ | ✅ |
| 生命連結對隊友 B（治 B） | ❌ | ❌ |
| 防護（同時治 A + B） | ✅ | ✅ |
| 純食物 / 綁帶自癒 | ✅ | ✅ |

⇒ **`0x502A 存在 ⇔ 至少一筆 0x5029.target_id == 本地玩家角色 ID`**

### 3.3 使用方式

- **不要**把 0x502A 計入 HP 總量（會與 0x5029 重複）。
- 只用來：
  1. 快速判斷「本封包是否包含 self heal」
  2. 學習本地玩家角色 ID（見 §5）

---

## 4. 判別「治療目標」通則

```
∀ 0x5029 in payload:
    if 0x5029.target_id == 本地玩家角色 ID:
        分類為 self heal
    else:
        分類為 ally heal（或 other）

HP 總量、HPS 一律只從 0x5029 累計。
0x502A 僅作 flag / learning，不計入。
```

---

## 5. 本地玩家角色 ID 自動學習演算法

因為角色 ID 每次登入會變，且不能靠 config 硬編碼，用以下方法自動學習：

```
On each packet:
    找出所有 0x5029（記錄 target_id 與 heal 值）
    如果封包內有 0x502A:
        val = 0x502A.payload[9..12] 的 uint32
        candidates = { s.target_id : s ∈ 0x5029 且 s.heal == val }
        if |candidates| == 1:
            本地玩家角色 ID = candidates[0]   # 學到 → 快取
        elif |candidates| > 1:
            # 例如同封包多筆同值治療，暫時無法判斷
            # 用交集持續縮小；或搭配 session_token 交叉驗證
            pass
```

一旦學到就快取到 session 結束。之後每個 0x5029 直接分類即可。

**輔助交叉驗證**：`0x502A.session_token == 對應 0x5029.session_token`。同 session 應恆等；不等則資料異常。

**已知限制**：目前唯一的自身 ID 來源是 0x502A。在治療事件發生前（例如剛登入、只受過傷害 / 護盾）**無法識別自身**，這段時間所有 target_id 都會被歸為「ally / other」。此問題待未來研究其他辨識管道。

## 6. 多目標同封包實例（frame 422，防護施放）

```
0x502A @ pos 9    | session_token(0x2000), heal=15   → 旗標：A 被治
0x5029 #1 @ pos 170 | target_id=0x8D2B3A(A), heal=15  → A 被治 +15
0x5029 #2 @ pos 337 | target_id=0x8D2BA0(B), heal=15  → B 被治 +15
```

**該封包實際治療**：A +15 + B +15 = **30 HP**  
若只算 self：**+15**

⚠️ 舊「pair dedupe」邏輯（150 B 視窗、prefer 0x5029）會誤算成 45 甚至更多，因為：
- 兩個 0x5029 都超出 150 B 視窗（161 B、328 B）→ 都被視為「無 pair」
- 0x502A 被當 solo companion 也計入
- 三筆全都獨立算，且沒有目標過濾

---

## 7. 實作修訂建議（治療）

- **移除 pair / 配對視窗概念**：舊有「0x502A 與 0x5029 於 150 B 內配對、擇一計入」的邏輯要整段拿掉。
- **0x5029 每筆獨立發成 HealEvent**：一封包內多個 0x5029 全部各自計入（多目標技能會有這種情況）。
- **0x502A 只當旗標**：不計入 HP / HPS，改為觸發「本地玩家 ID 學習流程」（§5）。
- **加入 `local_player_char_id` 快取**：session 內學到一次就固定，之後每個 0x5029 依 `target_id` 分成 self / ally 兩類。
- **HPS 建議分兩條列**：自癒 HPS、對隊友 HPS，符合多目標技能的實況。

好處：
- 修正「防護」等多目標技能的漏計 / 誤計
- 可精準區分「自己被治」vs「治療隊友」
- HPS 分自癒 HPS / 團體 HPS 兩條列

## 8. 護盾（Shield）

透過 `WS1-找護盾.json` frame 364（防護施放完整封包）鎖定**兩個** shield opcode，各司其職。

### 8.1 `0x00004EED` — 本次獲得的護盾增量（主）

```
ed 4e 00 00  18 00 00 00           # cmd 0x00004EED, size 24
[00] [target_id:8] [shield_amount:8 uint64 LE] [flag:8]
```

| payload offset | 長度 | 意義 |
|---|---|---|
| 0 | 1 | tag `00` |
| 1..8 | 8 | target_id |
| **9..16** | **8** | **★ 本次獲得的護盾量（uint64 LE）** |
| 17..24 | 8 | flag，樣本恆為 `00 00 08 00 00 00 00 00` |

Frame 364 樣本：
| target | shield_amount | 對照遊戲顯示 |
|---|---|---|
| A (0x8D2B3A) | **88** (0x58) | ✅ 完全一致 |
| B (0x8D2BA0) | **769** (0x301) | ✅ 完全一致 |

**信心：高**。全檔 `58:00:00:00` 只出現這 1 次，且同一封包內成對出現 A、B 兩筆，語意乾淨。

### 8.2 `0x0001B1B3` — 護盾累計後總量

```
b3 b1 01 00  18 00 00 00           # cmd 0x0001B1B3, size 24
[00] [target_id:8] [total:8 uint64 LE] [total_dup:8 uint64 LE]
```

| target | total | total_dup |
|---|---|---|
| A (0x8D2B3A) | **265** (0x109) | 265 |
| B (0x8D2BA0) | **769** (0x301) | 769 |

**推測**：施放後的護盾總量。B 原本無護盾 → 0 + 769 = 769；A 原本殘留 177 護盾 → 177 + 88 = 265。可作為「校正 / 狀態同步」使用。

### 8.3 判別「護盾對象」

護盾 opcode **沒有** 0x502A 這類的 self-flag，但兩個 opcode 都直接帶 target_id，可以套用同一套規則：

```
∀ 0x00004EED / 0x0001B1B3 in payload:
    if target_id == 本地玩家角色 ID:
        分類為 self shield
    else:
        分類為 ally shield
```

**注意**：判別依賴 `local_player_char_id`，而該 ID 目前只能從 0x502A 學到（見 §5 限制）。在治療事件發生前，無法判別護盾對象是否為自身。

### 8.4 實作建議

- **統計「本次獲得護盾」用 `0x00004EED`**（乾淨、單一值、對得上遊戲）
- **顯示「當前護盾總量」用 `0x0001B1B3`**（狀態同步）
- 護盾 UI 建議：綠色 / 藍色列（區別於治療的綠色）、數值 `+N Shield`、標籤 `[護盾]`
- 護盾統計獨立於 HP / HPS，不混計

## 9. Skill ID 提取

治療（`0x5029`）與護盾增量（`0x4EED`）本身**不含 Skill ID**，需另外從同 payload 內的 skill TLV 掃描取得。

### 9.1 掃描規則

- 對每一筆 `0x5029` 或 `0x4EED`，在**同一 TCP payload** 內做雙向 Near scan（±300 bytes）尋找 skill TLV
- 兩種 skill TLV 皆帶 Skill ID 於 header+25：
  - **`0x00004FC5`** size 35（經典型，同傷害面）— 無條件接受
  - **`0x0001ADE8`** size 36（替代型）— **必須緊接 `0x4EED` 結束**（gap 0..8B），否則視為 decoy
- 排名：距離最小者勝，平手偏 after
- 無候選 → Skill ID 為 `null`（不捏造、不從傷害 TLV 借用）

### 9.2 開放問題：`0x1ADEA` 是否也是 tick-side skill TLV？

觀察：治療 tick 封包（例如 frame 24 生命連結 +10 to B）內含 **`0x0001ADEA`**（末位 `EA`）而非 `0x0001ADE8`（末位 `E8`）。結構同 size 36，header+25 位置可讀出一個 uint32（frame 24 樣本為 `0x3D36850A`）。

- 若 `0x1ADEA` 是「tick 版動作事件」且 +25 為 skill / effect ID → 應納入 §9.1 作為第三個候選格式
- 若不是 → 明確排除，避免誤匹配

**待驗證方式**：對比不同技能（例如生命連結 tick / 綁帶 / 食物）的 tick 封包 `0x1ADEA` +25 值，看是否隨技能變動：
- 隨技能變 → 是 skill / effect ID
- 恆定或隨其他因素變 → 不是
